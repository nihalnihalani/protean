Authors: Dayuan Fu, Mohan Jiang, Tongyu Wang, Dian Yang, Jiarui Hu, Liming Liu, Jinlong Hou, Pengfei Li
Date: 2026-06-15

## One-Sentence Summary

daVinci-kernel trains an LLM system for CUDA/Triton kernel optimization by jointly evolving a skill library, selecting relevant skills for each task, generating optimized kernels, and summarizing verified successful rollouts back into reusable skills.

## Core Idea

GPU kernel optimization is treated as a performance-improvement task, not a pure correctness task. The paper argues that as the model improves, simple broad tricks stop being enough; harder tasks need reusable, task-specific optimization knowledge. daVinci-kernel therefore couples policy learning with an evolving skill library.

## Architecture

The system has three agents that share one LLM backbone:

1. Skill Selection Agent
   - Retrieves relevant optimization skills.
   - Uses BM25 plus LLM reranking.

2. Policy Agent
   - Generates multi-turn CUDA/Triton kernels.
   - Conditions generation on selected skills.

3. Skill Summary Agent
   - Distills successful rollouts into reusable skills.
   - Adds candidate skills only after execution-based verification confirms reproducible speedups.

All three agents are initialized with structured SFT and then optimized with multi-turn REINFORCE plus per-agent advantage estimation.

## Reported Results

On KernelBench, daVinci-kernel-14B reports Fast1 scores:

- Level 1: 37.2%
- Level 2: 70.6%
- Level 3: 32.2%

The paper reports stronger performance than Dr. Kernel-14B, with the largest practical value on harder tasks where skill reuse matters more.

## Ablation Takeaways

The ablations support these claims:

- Removing inference-time skill injection causes a large drop, especially on difficult tasks.
- Training without joint selection and summarization weakens high-threshold speedups.
- BM25-only retrieval can help with shallow speedups, but does not reliably support harder optimization thresholds.
- The gains are not just model scaling; they come from the skill evolution loop.

## What Protean Should Borrow Now

Keep only the pieces that fit the lean verifier-first MVP:

- Execution-based verification before trusting an optimization.
- Reusable notes about successful kernel tricks.
- Static skill notes as optional prompt context later.
- A clear distinction between correctness and speed reward.

## What Protean Should Not Build Yet

Do not add these to the current critical path:

- Three jointly trained agents.
- Multi-turn REINFORCE.
- Dynamic skill summarization.
- LLM reranking for skill selection.
- Full daVinci-style training loop.

Those are research extensions. Protean v1 is intentionally smaller: two ops, one verifier, one HUD wrapper, and concrete PyTorch-vs-Triton deltas on held-out shapes.

## Relationship To Protean

Protean is not a daVinci-kernel clone. Protean uses the paper as supporting evidence that:

- Kernel optimization is a legitimate RL target.
- Execution-measured speedup is a meaningful reward.
- Reusable kernel optimization skills matter.

Protean's differentiator for the hackathon remains simpler and narrower:

- held-out shape grading,
- a fail-closed verifier,
- a concrete PyTorch-eager vs hand-written Triton benchmark,
- small repo surface area that can grow incrementally.

## Useful Pitch Sentence

daVinci-kernel shows that reusable optimization skills improve kernel-generation RL; Protean starts one layer lower by making the verifier and held-out shape benchmark small, inspectable, and hard to fake.
